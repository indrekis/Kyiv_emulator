# RK4 на програмній МП ЕОМ «Київ» — два кроки (функціональна реконструкція)

**Нативно підтверджено:** `PASS_H115_B16_R1_BOUNDED_SUM_RK4_NOT_HISTORICAL`. Одна неперервна сесія продукційного CPU: **1637 машинних команд, 50 FP-операцій, 54/54 контрольні точки, два кроки RK4, одна зворотна гілка й дві умовні перевірки**. Ця програма — сучасна FP-адаптація, **не історична** програма Рунге—Кутти з `libs/runge_kutta.txt`. Остання використовує fixed-point і відрізняється форматом даних, адресацією й інтерфейсом.

## Задача й результати

Розв'язуємо `y'(t) = -y(t)`, `y(0) = 1`, `h=1/4` класичним RK4:

    k1 = -y
    k2 = -(y + h*k1/2)
    k3 = -(y + h*k2/2)
    k4 = -(y + h*k3)
    y_next = y + h*(k1 + 2*k2 + 2*k3 + k4)/6.

Для конкретних початкових умов перевірені **побітово точні** машинні слова:

| Крок | t | y (RK4) | Десяткове значення |
|---:|---:|---:|---:|
| 0 | 0 | 1 | 1 |
| 1 | 1/4 | **1595/2048** | 0.77880859375 |
| 2 | 1/2 | **2544025/4194304** | 0.6065428256988525390625 |

Незалежний математичний еталон для `y'=-y` — многочлен стійкості `R(-h)=1-h+h²/2-h³/6+h⁴/24=1595/2048`: після двох кроків `y=R(-h)²`. Це еталон **RK4**, не аналітичний розв'язок `exp(-t)`. В усіх 50 тестових FP-операціях вихід точно представляється в 41-бітному форматі, тому немає допусків або невизначеності округлення.

## Чому використано компенсоване накопичення

Звичайна реалізація `k2+k3` у попередньому H115-B16 на адресі `0252` зламалася на додаванні двох від'ємних чисел: замість `−113/64` обчислено `+15/64` — різниця рівно **+2** через переповнення мантиси. Цей **окремий дефект FP-МП досі відкритий**, хоча його вдається обійти зміною порядку обчислень.

Тут машинна програма замість небезпечного прямого підсумовування обчислює

    r = (1 + k1/8 + k2/4 + k3/4 + k4/8) - 1
    delta = 2*(r/6)
    y_next = y + delta.

Для `h=1/4` це алгебраїчно та чисельно еквівалентно класичному RK4 в межах перевірених **точно представних** проміжних результатів. Прийняття цього прикладу **не означає виправлення загальної FP-арифметики**. Оригінальний H115-B16 `HOLD` збережено у `reference/B16_HOLD_EVIDENCE_V1.zip` як регресійний негативний контроль.

## Машинний образ і інтерфейс МП

Усі адреси вісімкові. [`inputs/RK4_IMAGE.k41`](inputs/RK4_IMAGE.k41) містить **47 машинних записів**, із яких користувацькі команди розміщені в `0240–0273` (25 FP-арифметичних, умовне розгалуження `0271`, зворотний перехід `0272`, кінцевий STOP-маркер `0273`). Значення й проміжні змінні розміщені у `0100–0131` поза службовою ОЗП МП `0001–0032`.

- `0100`: y; `0101`: t; `0102`: h=1/4; `0103`: h/2=1/8; `0104`: 2; `0105`: 6.
- `0106`: 0; `0107`: поріг 3/8 для умови завершення; `0110`: 1 для компенсованого накопичення.
- `0120–0126`: k1, a, k2, b, k3, c, k4; `0127`: r; `0130`: масштабована сума/приріст; `0131`: порівняльна різниця d.
- `0240–0251`: обчислення чотирьох стадій k1–k4.
- `0252–0265`: компенсоване накопичення та приріст y.
- `0266–0270`: оновлення y, t й перевірка `d=3/8-t`.
- `0271`: умовний вихід (`31`); `0272`: машинний перехід назад; `0273`: STOP-маркер, **не виконується** в прийнятому маршруті.

Команди користувача **не можна виконувати безпосередньо в апаратному fixed-point режимі CPU**. МП інтерпретує їх через ROM-диспетчер (вхід `3300`, користувацький початковий покажчик `0240` задається через NK `3000`). Після початкового пуску HOST не змінює PC і не підміняє міжкрокові результати.

## Повторення результату офлайн (Python 3.10+)

Із кореня checkout:

```bash
python -B examples/fp_rk4_reconstructed/run.py --selftest && \
python -B examples/fp_rk4_reconstructed/run.py --offline && \
python -B -m unittest discover -s examples/fp_rk4_reconstructed/tests -p 'test_*.py' -v
```

Ці команди повторно перевіряють збережений `evidence/H115_B16_R1_FP_RK4_BOUNDED_SUM_EVIDENCE_V1.zip`: CRC і всі SHA-256, 1637 рядків CPU-траси, 54 контрольні точки з 12 FP-комірками, відсутність виконання користувацьких команд напряму і недрукованого `3574`. Вони також звіряють незалежний раціональний оракул, внутрішній образ і початковий H115-B16 `HOLD`. **Це аудит наявного нативного результату, не новий запуск CPU.** Не потрібні мережа, сторонні Python-пакети чи тимчасова папка H115-B16-R1.

## Нативне виконання (MSYS2 MINGW64)

Потрібні GCC/G++ (C++17), Python 3.10+ і незмінні кваліфіковані джерела CPU та ROM. Джерельні Git-blob і SHA-256 перевіряються перед компіляцією; це важливо, бо історична точність реконструкції не доведена.

```bash
python -B examples/fp_rk4_reconstructed/run.py --native --repo . \
  --out tempkyiv/FP_RK4_NATIVE_REPLAY_01
```

Новий output завжди створюється під `tempkyiv/`; наявні evidence-файли не перезаписуються. При помилці компіляції, старті чи контрольній точці отримуємо `HOLD` із доступними трасами в окремому ZIP. [`native.cpp`](native.cpp) — **побайтово незмінений** harness H115-B16-R1.

Цей тест використовує приватні ROM-патчі МП за Глушковим і Ющенко (1962): `3455`, `3467`, `3470`, `3474`, `3476`, `3706`, `3707`. Ці сім слів функціональної реконструкції відокремлені від джерельної 251-слівної транскрипції. `3706`, `3707` не надруковані, слово `3574` залишається **невідомим** і не доповнюється; зміни CPU/ROM-файлів не проводяться.
