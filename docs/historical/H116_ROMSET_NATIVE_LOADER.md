# H116-C1b — атомарне встановлення ROM-комплектів під час запуску CPU

**Статус до нативного гейта:** `C1B_CANDIDATE_NOT_YET_NATIVE_ACCEPTED`.
**Область:** тільки явний HOST `image` opt-in; продукційний `Kyiv_t` та його ISA не змінюються. Гарячої заміни ROM немає.

## Повний шлях від JSON до CPU

1. `tools/historical/rom_catalog_v1.py validate SET`: прочитати JSON маніфести, SHA кожного оригінального `.k41`, фізичні слоти та колізії; невідомі слова не заповнювати.
2. `prepare SET --out tempkyiv/NAME`: створити нову папку з `replaceable.k41`, `RESULT.json`, `SHA256SUMS.txt`. Ця дія **не виконує CPU**.
3. `kyivemu image PROGRAM ENTRY LIMIT --rom-set-image .../replaceable.k41 --rom-set-sha256 SHA [--watch ADDR]`: C++ повторно читає і перевіряє SHA **тих самих байтів**, які парсить, а також вісімкові адреси 3300–3777, 41-бітну ширину, порядок та відсутність дублікатів. Перевірка RAM-програми та постійного ROM передує конструюванню нового відкладеного `Kyiv_t`. Лише після повного preflight встановлюється підготовлений комплект і стартує CPU.

**Приклад MSYS2 MINGW64 (корінь репозиторію):**

```sh
python -B tools/historical/rom_catalog_v1.py prepare math_module1 \
  --out tempkyiv/c1b_module1_prepare && \
ROM=tempkyiv/c1b_module1_prepare/replaceable.k41 && \
SHA=$(sha256sum "$ROM" | cut -d' ' -f1) && \
g++ -std=c++17 -O0 -Iinc src/main.cpp src/asm_disasm.cpp -o tempkyiv/kyivemu.exe && \
tempkyiv/kyivemu.exe image examples/historical/gy1962/au1_logic.k41 0043 1 \
  --rom-set-image "$ROM" --rom-set-sha256 "$SHA" --watch 3300
```

Для FP-програм уже наявний `fp-image` приймає `replaceable.k41` через `--fp-rom` та `--fp-sha256`, без зміни його машинної семантики. Зокрема, `fp_functional` можна підготувати через каталог C1a та виконувати з тією самою програмою Ейлера.

## Додавання нових модулів

1. Створити новий `.k41` за межами `tempkyiv` із явними машинними словами.
2. Додати `examples/rom_catalog/modules/ID.json`: шлях, SHA-256, список фізичних слотів, кількість слів, provenance, `critical_unknown`.
3. Додати/оновити `examples/rom_catalog/sets/NAME.json`: обрані ID модулів та SHA постійного ROM.
4. `validate`, `prepare`, `sha256sum` і запуск. **Код C++ та Python не змінюється.** Можна включати декілька різних модулів за умови відсутності колізій слотів.

Для неповного ROM-комплекту наведені лише відомі слова. Неоголошені слова залишаються невідомими **у каталозі**. У пам'яті `Kyiv_t` ненадані комірки залишаються початковими (як правило, нуль), але це **не є історичним значенням і не є source PASS**. Надрукована МП 1962 року (251 слово) та реконструйована МП H115 (257 слів) — окремі конфігурації, не взаємозамінні історично.

## Гарантія транзакційності та обмеження

- Якщо помилкова SHA, неприпустима адреса, дубль, надшироке слово, невідомий опціон або несумісний запуск, активна машина **не змінюється**, бо вона ще не існує. Гарантія стосується **підготовки та запуску нової CLI-сесії**, а не заміни активного CPU в GUI.
- `--rom-set-image` потребує `--rom-set-sha256` і навпаки. Його не можна поєднувати з `--rom-module1` чи RAM-програмою з `--allow-rom` (щоб не допустити прихованих ROM-перекриттів). Початкове `image` без нових прапорців і старий `--rom-module1` залишаються без змін.
- У режимі `image` ROM не використовується як підстава для перевірки коректності чисел або історичної автентичності. C++ перевіряє завантажений образ і його SHA; **належність до конкретного JSON-комплекту підтверджує тільки окремий Python preflight C1a**. Синтетичні образи для тестів маркуються `SYNTHETIC_TEST`.
- Для повноцінного GUI збереження/перемикання екземплярів CPU, операторського стану й чекпойнтів є окремим контрактом майбутнього C2/H1. Під час виконання CPU гарячої заміни немає.
- Нативні CPU випробування виконуються лише на машині користувача, а не при офлайновій підготовці пакета.
