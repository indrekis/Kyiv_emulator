# H116-C2a — декларативні сценарії ROM-комплектів

**Контракт:** `KYIV_H116_ROM_SCENARIO_V1`. Це сучасна HOST-оркестрація, **не історичний формат сценаріїв пульта**. Машинні інструкції виконує незмінений продукційний CPU (`Kyiv_t`) через CLI `image` або `fp-image`. Арифметичних інтерпретаторів у Python немає.

## Додавання нового сценарію

1. Обрати наявний або створити новий ROM-комплект через `examples/rom_catalog/modules/*.json` і `sets/*.json` (H116-C1a). Додати новий модуль можна тільки за допомогою `.k41` та JSON, без правок C++/Python.
2. Підготувати **RAM**-програму `KYIV41-OCT1` і порахувати SHA-256 її фактичних байтів. Змінно-спаяний ROM і RAM-програма не змішуються в одному образі.
3. Додати `examples/rom_scenarios/NEW_ID.json`: `rom_set`, `program.path`, `program.sha256`, `mode` (`image`/`fp-image`), `entry`, `max_steps`, `end_pointer` (лише FP), очікувані `status`, `steps`, `dispatches`, та адресу→14-значне машинне слово для кожного `watch`.
4. Виконати `validate NEW_ID`, далі `run NEW_ID --exe ... --out tempkyiv/NEW_OUTPUT`. Runner спершу повністю перевіряє сценарій, каталог і SHA програми, готує розріджений ROM-комплект, запускає існуючий CLI через `subprocess` **без shell** та перевіряє машинні результати. При невідповідності повертає HOLD. Каталог і runner не змінюються при додаванні нового ID.

Зразок у MSYS2 MINGW64 із кореня checkout:

```sh
mkdir -p tempkyiv/c2a_manual_bin/mem && \
cp mem/ROM.txt tempkyiv/c2a_manual_bin/mem/ROM.txt && \
g++ -std=c++17 -O0 -Iinc src/main.cpp src/asm_disasm.cpp -o tempkyiv/c2a_manual_bin/kyivemu.exe && \
python -B tools/historical/rom_scenarios_v1.py validate fp_affine && \
python -B tools/historical/rom_scenarios_v1.py run fp_affine \
  --exe tempkyiv/c2a_manual_bin/kyivemu.exe --out tempkyiv/c2a_affine_manual_01
```

> Для `fp-image` фіксований ROM шукається від розташування виконуваного файла (див. H115). Наведена команда створює приватну копію фіксованого `mem/ROM.txt` поруч із CLI. Gate так само створює `bin/mem/ROM.txt`. Робочий `mem/ROM.txt` ніколи не модифікується.

Для fail-closed приймання ще **не встановленого** сценарію runner підтримує
`--program-staging-root ABSOLUTE_PATH`: тільки каталог усередині `tempkyiv/`,
і лише для нової RAM-програми, відсутньої у tracked `examples/`.
На програму поширюється звичайна SHA-256 перевірка, а після встановлення
цей параметр не потрібен. За наявності tracked файла він має пріоритет.

## Перші чотири сценарії

| ID | ROM-set | Обсяг/очікуваний результат | Що це підтверджує |
|---|---|---|---|
| `romset_smoke` | `math_module1` | RAM STOP за одну команду, слово `ROM[3300]` | Завантаження блока №1, **не** чисельне виконання sqrt |
| `fp_euler` | `fp_functional` | 623 команд, 24 диспетчеризації; `81/256`, `t=1` | H115 FP Ейлер на продукційному CPU |
| `fp_rk4` | `fp_functional` | 1305 команд, 42 диспетчеризації; `2544025/4194304` | Первісний FP RK4, **не** fixed-point блок №4 |
| `fp_affine` | `fp_functional` | 623 команд, 24 диспетчеризації; `31/64` | Нова FP-програма незалежно від двох методів |

## Безпека й межі

- ROM-слоти, джерела, SHA та колізії перевіряє **C1a**, а атомарне встановлення на *новий* CPU — **C1b**. `fp-image` використовує свій раніше прийнятий SHA-перевірений шлях, який теж створює новий CPU. Гарячої заміни немає.
- `run` завжди створює новий каталог у `tempkyiv/`; не перезаписує наявні результати, історичні образи, ROM або код CPU. При HOLD каталог із діагностикою зберігається.
- Результат `LIMIT` **не** вважається успішним завершенням ні `image`, ні `fp-image`. Для `image` вимагається `CPU_STOP`; для FP — `END_POINTER`. Кількість кроків/диспетчеризацій і всі задані слова порівнюються точно.
- Програми та очікувані значення — **HOST-функціональна реконструкція**. Це не hardware oracle, не реконструкція всіх фізичних дій оператора, не засвідчення історичної програми RK4. Відсутнє історичне слово `3574` не заповнюється автоматично.
- Обмеження першої ітерації: поки є лише стартовий NK, який встановлює існуючий `fp-image`; довільна послідовність операторських дій, disk checkpoint і Qt chooser увійдуть у C2b/H1 окремо. Сценарний формат буде еволюціонувати версіоновано, без руйнування V1.
