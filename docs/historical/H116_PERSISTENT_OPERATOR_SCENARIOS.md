# H116-C2b — декларативні операторські дії у постійній сесії

**Статус кандидата:** `H116_C2B_NATIVE_GATE_PENDING`; жодної претензії на фізичний пульт чи історичний наскрізний AU PASS.

## Мета

`tools/historical/operator_scenarios_v1.py` виконує скінченний JSON-сценарій у **одному** процесі `gui/qt6/kyiv_gui_backend.cpp`, який використовує продукційний `Kyiv_t`. Жодного повторного тлумачення машинних інструкцій у Python немає. Для змінної ПЗП вхідний ROM-комплект підготовлюється валідатором C1a, перевіряється SHA-256 у C++ C1b й встановлюється разом із постійним ROM **до LOAD**. Нові модулі надалі додаються як `.k41` + JSON; нові сценарії — як JSON, без редагування runner-а чи C++.

Стандартний виклик backend `kyiv_gui_backend.exe mem/ROM.txt` збережено без змін. Новий opt-in:

```text
kyiv_gui_backend.exe mem/ROM.txt \
  --rom-set-image tempkyiv/prepared/replaceable.k41 \
  --rom-set-sha256 <64-hex>
```

`PING` додає `ROMSET_SHA256` тільки коли комплект вибрано. `LOAD` зберігає атомарність: створює новий CPU, встановлює фіксовану ПСП та опційний ROM-комплект, читає RAM і тільки після всіх перевірок замінює активний CPU. **Гарячого перемикання ROM немає**. Файл `mem/ROM.txt` і `inc/kyiv.h` не змінюються.

## JSON-сценарій

`KYIV_H116_OPERATOR_SCENARIO_V1` містить `id`, `description`, `origin`, `rom_set`, `program: {path,sha256}`, `entry`, `max_steps`, `actions`. Він використовує C1a для суворої перевірки ROM-комплектів і окремий SHA-pinned парсер RAM-образів, сумісний із `kyiv_host_image_v1` щодо порожніх рядків і коментарів `#`. Це важливо для канонічних історичних `.k41`, в яких збережено вихідні примітки; C1a ROM-парсер при цьому не змінюється. Поле `origin` кожної дії — `HOST_TEST`, `OPERATOR_DOCUMENTED` або `RECONSTRUCTED_ASSUMPTION`. Немає прихованого надання статусу історичної дії тестовій події.

Дії: `set_nk` (`3000–3002`, 41-бітове слово), `clear_nk`, `step` (1–32 команди з очікуваним `PATH`, числом виконаних команд та станом), `state`, `dump` (точні 14-цифрові слова), `save`, `restore`. Є глобальний ліміт запитаних кроків і максимум 64 дії. `restore` без `save` відхиляється на preflight.

Ці операторські дії — **сучасна HOST-реконструкція**. Вони не доводять ідентичність фізичним перемикачам реального «Києва». `3003–3007` не заборонені для звичайного машинного читання: підтримка фізичного пультового вибору тут існує лише для джерельно документованих `3000–3002`.

## Відтворення

З кореня репозиторію в MSYS2 MINGW64 (після встановлення):

```sh
python -B tools/historical/operator_scenarios_v1.py --repo . validate h9_nk_checkpoint
python -B tools/historical/operator_scenarios_v1.py --repo . validate fp_rom_nk_smoke
python -B -m unittest discover -s tests/historical -p 'test_h116_operator_scenarios.py' -v
```

Для запуску необхідний backend, скомпільований із `gui/qt6/kyiv_gui_backend.cpp` плюс продукційні C++ джерела; він має підтримувати необов'язкові `--rom-set-image/--rom-set-sha256`.

Приклад після звичайного `bash gui/qt6/run.sh --smoke-only`:

```sh
python -B tools/historical/operator_scenarios_v1.py --repo . run h9_nk_checkpoint \
  --backend tempkyiv/qt6_build/kyiv_gui_backend.exe \
  --out tempkyiv/my_h9_operator_run
```

`--out` має бути **новим** каталогом. Runner не змінює tracked файлів; логи та `RUN.json` / `HOLD.json` зберігаються в `tempkyiv/`. `PASS` означає лише bounded HOST/native observation; не апаратний oracle.

## Приймальні перевірки та обмеження

- H9: панель `NK3000`, `SAVE`, один CPU крок у `0143`, слово `RAM[0347]`, вимкнення панелі, `RESTORE`, повторний крок і той самий результат — **в одній CPU-сесії**.
- FP-set: новий спосіб встановлення функціонального H115 ROM у постійний backend, вибір `NK3001`, читання пульта/шафи, checkpoint, один CPU STOP з RAM. Це **не** нове числове FP-приймання.
- Режим GUI без обраного ROM-комплекту зберігає старий протокол `PROTOCOL=1` і поведінку `LOAD`/`SAVE`/`STEP`/`RESTORE`.
- Негативні тести перевіряють SHA, підміну оракула, некоректні адреси й ліміти, відсутнє `SAVE` та неправильне походження дії.
- Немає складених декількох незалежних програм в одному RAM-образі, емуляції фізичного пульта чи доказу повного тесту АУ. C2a й C2b залишаються різними декларативними режимами поверх одних каталогів і продукційного CPU.

## R1: сумісність із коментарями історичного RAM-образу

V1 `HOLD` на `h9_nk_checkpoint` виник до виконання CPU: суворий парсер
ROM-модуля відхилив коментарі в історичному `.k41`. У R1 RAM-парсер
приймає порожні рядки і коментарі `#`, але зберігає SHA-256 вихідних
байтів, перевірки 41 біт, унікальності адрес і заборону запису в ROM.
Нативний PASS та історичний hardware oracle не припускаються.
