# H116-C1a — розширюваний каталог змінних ROM-модулів ЕОМ «Київ»

**Область:** декларативний, read-only HOST-каталог із валідатором і підготовкою комплектів. **Це не завантажувач ROM у продукційний CPU і не історичний hardware oracle.** Продукційні `src/`, `inc/`, `mem/ROM.txt`, вже прийняті образи та GUI не змінюються. Приймання — після запуску гейта H116-P0/C1a на локальному checkout.

## Чотири незалежні складники

1. **Образ модуля** `.k41`: рівно відомі 41-бітові слова в сучасному форматі `KYIV41-OCT1`. Історичні транскрипції не модифікувати; реконструкції тримати окремо.
2. **Опис модуля** `examples/rom_catalog/modules/<id>.json`: незмінний id, шлях до **єдиного** канонічного `.k41`, SHA-256 точних байтів, повні 64-слівні адресні *слоти*, число відомих слів, походження, критичні невідомі адреси. Відсутні слова в слоті залишаються **відсутніми**, а не заповненими нулем.
3. **ROM-комплект** `examples/rom_catalog/sets/<id>.json`: список ID модулів, сумісних за неперетинанням **слотів**, і SHA фіксованої ПСП. Склад задається явно; одночасне встановлення модуля № 1 та FP-інтерпретатора відхиляється до будь-яких змін у машині.
4. **Сценарій** (майбутній C2): комплект + образ RAM + НК/операторський стан + обмеження виконання + окремий oracle. Сценарії **не** входять у C1a.

## Фізична адресна карта та правила

- `3000–3007`: НК / пультові джерела — **не** змінні ROM-модулі, не забороняємо законні машинні читання цих адрес.
- `3010–3277`: фіксована ПСП із `mem/ROM.txt`, SHA-256 `a1d9c28e969fa1d74966a78fdbb1bf85b4c45354a764cb8665a73b0a62bdab38`, не копіювати в модулі.
- `3300–3777`: п’ять слотів по 64 десяткові адреси: `3300–3377`, `3400–3477`, `3500–3577`, `3600–3677`, `3700–3777`. Маніфест декларує **повні слоти**, навіть якщо `.k41` розріджений: слотові колізії відхиляються, навіть якщо списки відомих слів не перетинаються.
- `3777`: потенційна апаратна особливість залишається відкритою. C1a лише читає/валідує слово з явно підписаного образу; **не** імітує спеціальну поведінку цієї адреси.
- Фіксатор значення за SHA — технічний контроль цілісності, не свідчення історичної правильності. `source` і `functional` комплектам присвоєно різні ID та статуси provenance.

| `fp_1962_printed` | `examples/historical/gy1962/rom_modules/fp_simulation_251_printed.k41` | 5 | 251 | `SOURCE_TRANSCRIPTION`, історичне виконання OPEN |

## Команди (після приймання C1a)

З кореня Git checkout:

```sh
python -B tools/historical/rom_catalog_v1.py list
python -B tools/historical/rom_catalog_v1.py validate math_module1
python -B tools/historical/rom_catalog_v1.py validate fp_1962_printed
python -B tools/historical/rom_catalog_v1.py validate fp_functional
python -B tools/historical/rom_catalog_v1.py prepare fp_functional --out tempkyiv/h116_fp_candidate_01
```

`prepare` створює **новий** каталог із `replaceable.k41`, `RESULT.json` і `SHA256SUMS.txt`; ніколи не перезаписує наявне. `replaceable.k41` містить тільки реально визначені слова, а звіт явно перелічує невідомі адреси. Цей файл можна **окремо** подати до відповідного перевіреного HOST-завантажувача; C1a його не встановлює в CPU.

## Як додати новий модуль — без редагування Python/C++

1. Покласти новий `.k41` у `examples/` під власним ім'ям, додати окремий provenance (`SOURCE`/`RECONSTRUCTED_ASSUMPTION`/`SYNTHETIC_TEST`) і незалежні свідчення за можливості.
2. Створити `examples/rom_catalog/modules/my_module.json` за зразком одного з трьох чинних файлів, указати SHA-256 реального `.k41`, повні слоти, кількість записів і список критичних невідомих адрес.
3. Створити `examples/rom_catalog/sets/my_set.json` зі списком `modules` (можна вибрати **кілька** несумісних за нульовим перекриттям слотів модулів). Жодного редагування реєстратора або умов `if module_id == ...` не потрібно.
4. Запустити `validate my_set`; виконати негативні тести на колізії, підміну SHA, невідомі слова; після C1b перевірити реальний нативний запуск з явно вибраним комплектом.

Приклад полів модуля:

```json
{
  "schema": "KYIV_H116_ROM_MODULE_V1",
  "id": "my_module",
  "description": "Explicitly described module; provenance to be supplied",
  "image": "examples/my_module/words.k41",
  "sha256": "<64 lowercase hex characters of exact bytes>",
  "slots": [["3400", "3477"]],
  "records": 3,
  "provenance": "RECONSTRUCTED_ASSUMPTION",
  "critical_unknown": ["3407"]
}
```

Новий модуль не повинен займати слоти уже вибраного комплекту. Якщо `.k41` має менше 64 слів, це **не** означає, що решту дозволено автоматично матеріалізувати нулями.

## Границі C1a та наступний C1b

C1a реалізує лише `list`, `validate`, `prepare`. Не модифікує CPU, ROM, NK, Qt, реєстр прикладів, не запускає нативний CPU і **не гарантує**, що всі задекларовані модулі виконуються правильно. `fp-image` H115 і `--rom-module1` H58 залишаються як раніше.

**C1b** має повторно використати ці маніфести й реалізувати єдиний транзакційний startup: всі файли/слоти/хеші/НК/пам'ять перевіряти **до** створення/зміни CPU; явний вибір `--rom-set` і `--rom-set-root` (синтаксис буде окремо затверджено), строгий ліміт кроків, regressions H58 та H115, негативні сценарії. GUI має споживати ту саму модель, а не створювати паралельний перелік модулів.

**Принцип публікації:** сучасний HOST-контейнер, SHA, функціональна реконструкція і історичний монтаж — різні поняття. Фізичної кваліфікації ПЗП немає. До C2 не додавати недокументовані початкові значення RAM/НК; користуватися класифікацією припущень із ROADMAP.
