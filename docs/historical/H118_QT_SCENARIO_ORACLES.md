# H118 — вбудоване відтворення C2b та машинні oracle C2a в Qt

**Статус документа:** кандидат для native та ручного Qt acceptance, **не** твердження про історичний hardware-oracle. База: `main` / `357726264b7a193cfe0241495febc7a14aaa275e` (H117).

## 1. Мета та межі

H118 **не створює новий CPU**. Обидва режими використовують той самий наявний постійний `kyiv_gui_backend` з продукційним `Kyiv_t`.

- **C2a** — для сценаріїв `examples/rom_scenarios/*.json` існуючий SHA-pinned Python bridge надає Qt **вже валідований** еталон: статус завершення, число машинних команд, число відвідувань диспетчера МП (для FP), точні 14-цифрові вісімкові слова RAM/ROM. Після F6 в **тій самій CPU-сесії** Qt звіряє відповідь `STATE` та `DUMP`. Немає окремого виконання C2a через Python у GUI. На помилку виводиться `HOLD` з першою незбіжністю, не «PASS» після вичерпання кроків.
- **C2b** — окремий список `examples/operator_scenarios/*.json`. `qt_h118_operator_v1.py` викликає **чинний C2b валідатор** і C1a, готує приватну копію `.k41`, комплект ROM та план дій лише в `tempkyiv/`. Qt передає `LOAD/SETNK/CLEARNK/STEP/STATE/DUMP/SAVE/RESTORE` до **власного постійного backend**, порівнює всі заявлені поля відповіді до наступної дії й відображає журнал у вкладці трасування. Всі маніпуляції з НК та checkpoint реально відбуваються на цій CPU-сесії; немає другого виконавця інструкцій.
- **FP dispatcher count** — backend надсилає нове необов'язкове поле `DISPATCHES=N` у FP-відповідях, за семантикою H115 CLI (рахуються всі досягнення `PC=3305`, **включно** з кінцевою межею `END_POINTER`, де CPU інструкція не виконується). `SAVE/RESTORE` зберігає також лічильник; нефункціональні та старі сценарії не змінені. Поле є діагностикою, не додатковим арифметичним режимом. У регістрах GUI після завантаження FP-сценарію відображається «Дисп. МП: фактичне / очікуване» (для `fp_euler` після PASS — `24 / 24`). Лічильник оновлюється за відповідями продукційного backend після кроків і `RESTORE`, а для звичайних CPU-програм поле приховане. Якщо FP-програму запущено без C2a oracle, праве число — «—»; це не тест PASS.

**Поки не включено:** автоматизацію спеціального H117 двоепохного AU (його вже прийнятий окремий runner лишається доступним), нові числові джерельно кваліфіковані `.k41` для mathematical module 1 та fixed-point RK4. Їх не слід підмінювати `romset_smoke` або H115 FP RK4: це різні програми. Такі приклади — наступне розширення саме H118, не повернення до відкладених історичних прогалин.

## 2. Порядок ручної перевірки Qt

MSYS2 MINGW64, чистий checkout після пройдених native gates:

```sh
bash gui/qt6/run.sh
```

1. У **«Приклад»** обрати `fp_euler`, натиснути **«Завантажити»** та **F6**. У трасуванні очікується `PASS_H118_C2A_GUI_NATIVE_ORACLE_NOT_HARDWARE`. CPU: 623 машинні команди, 24 диспетчеризації МП, `END_POINTER`, слова `0100=12100000000077`, `0102=10000000000101`.
2. Аналогічно `fp_rk4`: 1305 команд, 42 диспетчеризації та `0100` з еталона JSON. Це **H115 FP-програма**, не fixed-point ROM №4. Також перевірити `fp_affine` і `romset_smoke` (RAM STOP).
3. У полі **«Сценарій оператора»** вибрати `h9_nk_checkpoint` і натиснути **«Відтворити й перевірити»**. Новий CPU почне з `0143`, виконає всі 15 C2b дій з реальною НК, `SAVE/RESTORE` і точними `DUMP`. Очікується `PASS_H118_C2B_GUI_PERSISTENT_HOST_NOT_HARDWARE`. Перевірити, що лампи/регістри в UI відображають стани тієї самої машини.
4. Перевірити `fp_rom_nk_smoke`: C2b підвантажить `fp_functional`, поставить НК3001, відновить checkpoint, виконає RAM STOP. Цей сценарій не є числовою FP-демонстрацією.
5. Після PASS повторно обрати звичайний H9/FP Euler: підвантаження іншого комплекту навмисно починає нову CPU-сесію без гарячої заміни ROM. Перевірити Manual Save/Restore, DUMP, F5 і відсутність зависання під час закриття GUI.
6. Негативні проби виконувати на приватній копії сценарію/неправильній SHA: валідатор має відхилити її **до** заміни попередньої активної CPU-сесії. Жодна SHA невідповідність не повинна показувати PASS.

Зміна НК або ручний Save/Restore під час C2a сесії скасовує право назвати її початковий oracle підтвердженим — Qt показує `HOLD` при перевірці. Для нового точного результату треба повторно **«Завантажити»**. Звичайний F5 дозволено, але граничне число команд усе одно перевіряється.

## 3. Нативні gates і обмеження доказів

- Офлайнові тести: H116 Qt bridge, H118 Python bridge (включно з path, duplicate output і SHA-блокуванням).
- Нативно: `bash gui/qt6/run.sh --smoke-only` із **приватного shadow checkout**, H116 C2a для всіх наявних числових сценаріїв, H116 C2b H9/FP-ROM у backend, перевірка нового FP `DISPATCHES=24` для Ейлера й Save/Restore. Після — окремий **ручний** продукційний Qt acceptance вище.
- `PASS_H118_C2A_GUI_NATIVE_ORACLE_NOT_HARDWARE` і `PASS_H118_C2B_GUI_PERSISTENT_HOST_NOT_HARDWARE` означають тільки заявлену функціональну область. Ні історичне виконання фізичного пульта, ні справжнє машинне слово АУ `0360`, FP-ROM `3574` чи RK4 `3677` звідси не випливають.
- Всі старі формати, `mem/ROM.txt`, оригінальні `.k41` та канонічний CPU недоторканні. Зміна C++ тільки в Qt frontend/backend протоколі; нативна арифметика `inc/kyiv.h`/`src/main.cpp` не змінюється.

## 4. Планові рішення

**H118-P1:** Qt C2a+C2b integration як один функціональний пакет, з native та ручним acceptance перед комітом.

**H118-P2:** додати в загальний каталог **тільки фактичні робочі source- або functional-scoped математичні сценарії** для блока №1 і fixed-point RK4, а також показ прийнятого H117 циклу АУ. Файл має містити точний тип доказу/масштабування та незалежний числовий еталон. Збережені H62/H100/H117 звіти — вихідний матеріал; не створювати новий історичний код і не обіцяти неіснуючі маніфести до проходження gate.

**Ключове рішення H117 залишається чинним:** `0360`, `3574`, `3200`, `3677`, інші історично невідомі стани та апаратні тонкощі мають статус `HISTORICAL_SOURCE_RESEARCH_DEFERRED` до нових даних. H118 — розвиток функціональності, не новий цикл археології.

## H118-R8 shared MINGW64 launcher and FP probe

The Python-to-Bash transition may drop `MSYSTEM`, `MINGW_PREFIX`, or select `/usr/bin/pkg-config`. The centralized launcher in `tools/historical/msys2_mingw64_v1.py` selects Bash from the same MSYS2 installation and re-establishes `MINGW64` inside the child process. Use it for subsequent Python-driven Qt acceptance. R7's native probe incorrectly expected `DISPATCHES` in `LOADFP`; R8 queries `STATE` after `LOADFP` and checks the actual wire contract without changing the backend or CPU.
