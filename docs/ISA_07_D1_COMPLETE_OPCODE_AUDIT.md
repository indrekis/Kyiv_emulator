# ISA-07 D1 — Повний реєстр кодів команд ЕОМ «Київ»

**База:** `d57ef2c` (ISA-06 D8-P10, 89/89 STRICT; 40/40 POLICY у фактичному журналі MSYS2 користувача). **Це read-only аудит**, а не патч CPU чи завершена специфікація ISA. Перевіряється 32 можливі п'ятибітові коди (вісімкові `00..37`): **30 відображених** у чинному C++ (рахуючи особливий `00`) та `36`, `37`, що *не відображені у чинних enum/dispatcher*. Не приписувати останнім історичний статус «заборонені» без окремого джерела.

## Умови доказовості

- **CODE_DEFECT:** дефект власне програмної логіки, встановлений за поточним C++ (наприклад, небажаний `switch` fallthrough чи читання неініціалізованої змінної). Це ще не доведення історичного виходу реального пристрою.
- **CODE_ANOMALY / CODE_SUSPECT:** конкретна поведінка реалізації, яку слід звірити з документованим переходом/форматом. Не виправляти, підставляючи вигадану семантику.
- **DOC, DOC_PARTIAL:** підтверджено лише зазначену частину семантики; **DOC_CONFLICT:** тексти/таблиці суперечать одне одному; **DOC_POLICY / POLICY_NOT_ORACLE:** перевірений варіант поведінки емулятора, а не апаратний оракул; **NO_CONFIRMED_SPEC:** поки немає підтвердженого нормативного правила.
- **STRICT 89/89; POLICY 40/40:** кількості конкретних перевірок у попередніх етапах, **не** 129 незалежних тестів для всіх 30 команд. Тривалі історичні RAM-прогони охоплюють підмножину ISA. Команди I/O `20..25` не мають кваліфікованого цільового тестового корпусу.
- `tests/isa/*`, попередні документальні аудити та поточний код — свідчення стану розробки, **не** самостійне історичне першоджерело. `STRICT` слід обґрунтовувати друкованими GY62/DPS64, а `OBS` не підвищувати без нового доказу.

## Файли реєстру

- `ISA_07_D1_OPCODE_MATRIX.tsv`: усі коди `00..37` (вісімкові), C++ символ, сімейство, програмний стан, рівень джерельного підтвердження, попередні тести і пов'язані питання. `existing_coverage` називає *етапи, що містять відповідні перевірки*, а не виміряне покриття всіх граничних значень.
- `ISA_07_D1_OPEN_ISSUES.tsv`: окремі незакриті питання з класом доказовості, пріоритетом, конкретною наступною перевіркою та походженням.
- `tools/isa07_d1_opcode_inventory_audit.py`: **статичний read-only** контроль повноти enum/dispatcher, 00, 36/37, зв'язків із реєстром, зафіксованих кодових симптомів I/O, Git blob CPU/заголовка. Ніде не запускає реальних пристроїв і не стверджує їхню правильність.

## Найвищий пріоритет — кодові дефекти I/O

1. **`22 → 23`**: обробник `opcode_write_perfo_binary` не завершується `break` і проходить у `opcode_write_magnetic_drum`. Як наслідок, одна команда може запускати два вихідні файлові сценарії. **CODE_DEFECT**, виявляється синтаксично. Перед виправленням — малий runtime-тест із тимчасовою директорією, що перевірить небажаний другий файл/перехід.
2. **`20` і `24`**: `bool flag;` використовується без ініціалізації в операторах умовного виходу з циклу. Це **невизначена поведінка C++**, незалежно від історичної семантики пристрою. Додати регресію на порожні/короткі файли та ініціалізувати прапорці.
3. **`21`**: локальний `counter` починається з 0, але не збільшується у циклі читання; пошук запису за `h > 0` не працює належним чином. **CODE_DEFECT**. Не плутати зі змінною `com_counter`, яка таки змінюється.
4. **`20/21/24/25`**: їхні обробники не змінюють `C_reg`, тому наступний крок CPU вибирає ту саму команду. Це **CODE_ANOMALY**, а висновок про потрібне історичне значення `C` — ще **OPEN**. Не застосовувати автоматичного `++C_reg` до звірки з GY62 і специфічними режимами I/O.
5. **`22/23`**: цикли `i=0..source_2` з читанням `source_1+i` потенційно плутають кінцеву адресу з довжиною (і в будь-якому випадку поведінка не узгоджена тестом для ненульового старту). Класифікуємо як **CODE_SUSPECT**, а не самочинно переписуємо.

Файлові шляхи `../../mem/...`, `../punched_tape.txt`, `../magnetic_drum.txt` та виклики `stoi/stol` без контрольованої обробки форматних помилок є додатковими ознаками **незавершеного I/O-адаптера**. Наразі не симулюємо аналогові ефекти носіїв, контактів чи часові характеристики.

## Невирішена цифрова семантика CPU

| Команди | Що саме відкрите | Чому попередні PASS недостатні |
|---|---|---|
| `07` | Carry у молодший біт; DPS64 с. 102 проти поточної `magnitude + 1` політики; точний `+0/-0` | Різні можливі повні 41-бітові коди, старі перевірки залишилися POLICY/OBS |
| `01` | Знак результату з модулем 0 за різних знаків доданків (M1) | Аудити H1–H9 залишили схеми C16/C17/C18 і F71 OPEN; історичний оракул не встановлено |
| `04/05` | `<` проти `<=` на рівності | Розбіжність тексту/таблиць; поточне `<=` збережено як POLICY |
| `30` | Модифікація II адресного поля перед записом у Р | GY62 с. 13 проти с. 57, обидва прочитання не можна оголосити STRICT |
| `26/27/34` | 10/11-бітні А/Ц, код `2000..2777`, крайова непряма адресація | GY62 с. 9/54 суперечить сама собі щодо Ц; цифровий тракт ще не кваліфіковано |
| `12` | Ділення на нуль; стан призначення та С при переповненні | Поточне зупинення — політика; потрібен документований маршрут |
| `06/35` | Знак нульової різниці модулів; перезапис перекритих адрес нормалізації | Немає достатнього опису пріоритетів усіх записів |
| `33` | С після STOP та режими контрольного останову | Окремо від тумблера аварійного переповнення |
| `36/37` | Є чи немає історичного визначення | Немає enum і case у поточному C++; не вигадувати значення |

Вже закриті помилки: `00` NOP, `02` різниця рівних чисел → `-0`, `03` знак початкового операнда II та overflow, `32` очищення Р, групові початкові адресні коди `26`, приріст А `27`, частина граничних випадків нормалізації `35`. **Не повертати їх до активних дефектів** на підставі застарілої документації ISA-01; нові підтверджені випадки все одно можуть відкрити додаткові питання.

## Рекомендована послідовність наступних етапів

1. **ISA-07 D2 — I/O behavior baseline**: без виправлень CPU написати ізольовані runtime-тести команд `20..25`, особливо `22→23`, `20/24 flag`, `21 counter`, усі потоки `C_reg`, інклюзивність діапазонів; використовувати тестові тимчасові файли, жодних реальних пристроїв. Репортувати окремо `CODE_DEFECT`, `DOC-MISMATCH`, `OBS`.
2. **ISA-07 D3 — minimal I/O fixes**: лише доведені програмні дефекти, кожен із регресійним тестом; історично невизначені переходи залишити явними POLICY до доказу.
3. **ISA-07 D4 — opcode 07**: зіставити цілочисельну модель, DPS64 p. 102 та цифрову схему формування переносу, зокрема випадки точного `|sum|=1`, `1+LSB`, `-0` і двох від'ємних операндів.
4. **ISA-07 D5 — targeted source review** `04/05`, `30`, А/Ц/Ф і, за наявності незалежних даних, `01`; змінювати CPU тільки при обґрунтованому нормативному очікуванні.
5. Після цього повернутися до першої історичної RAM-діагностики (колишній D8-P11), не змішуючи її з незавершеними I/O-підсистемами.

Цей план **не включає** затримки контактів, аналогові перехідні процеси та електричне моделювання. Принципові схеми застосовувати лише для конкретних цифрових питань (таких як знаковий нуль, перенесення, дешифрація команд).
